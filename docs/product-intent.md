# 모멘트리 제품 기획 의도

> 문서 상태: 현재 제품 기준
> 기준 앱: `apps/app` / `kr.co.uulab.momentry` / Expo SDK 57
> 마지막 정리: 2026-07-30

이 문서는 모멘트리가 왜 존재하는지, 누구를 위해 무엇을 제공하는지, 어떤 방향은 의도적으로 선택하지 않는지를 설명한다. 새로운 기능, 화면, 카피, 데이터 정책을 결정할 때 구현 편의보다 이 문서의 제품 원칙을 먼저 확인한다.

## 한 문장 정의

모멘트리는 오늘의 일상과 영화·책에서 만난 감정을 한곳에 쌓고 다시 꺼내 보는, 계정 없는 개인 기억 보관함이다.

## 이름에 담긴 의미

`Momentry`는 `Moment`와 `Entry`를 결합한 이름이다. 기록 한 건을 단순한 메모가 아니라 다시 돌아볼 수 있는 하나의 순간으로 본다.

브랜드가 말하는 “기억이 자라는 곳”은 기록량 경쟁을 뜻하지 않는다. 서로 다른 순간이 시간이 지나 하나의 개인적인 맥락을 만든다는 의미다. 다만 이 비유를 빈 화면과 통계 화면마다 반복하지 않고, 실제 화면에서는 날짜·기록·백업처럼 사용자가 바로 이해할 수 있는 말부터 보여준다.

## 해결하려는 문제

사람의 기억은 일기 앱, 영화 평점 서비스, 독서 노트와 사진첩에 흩어진다. 각 서비스는 자기 분야의 정보에는 강하지만, 사용자가 어떤 하루를 보냈고 무엇을 보고 읽으며 어떤 감정을 느꼈는지는 하나의 흐름으로 남기기 어렵다.

또한 기존 기록 서비스는 계정 생성, 공개 프로필, 팔로우, 추천, 피드, 연속 기록 같은 장치를 먼저 요구하기 쉽다. 기록을 공개하거나 성과처럼 관리하고 싶지 않은 사용자에게는 기록을 시작하는 비용이 된다.

모멘트리는 이 문제를 다음 방식으로 푼다.

- 일기, 영화, 책을 하나의 앱 안에서 같은 “기억”으로 취급한다.
- 계정 생성 없이 바로 기록하게 한다.
- 공개와 반응보다 작성, 보관, 검색, 재열람에 집중한다. 알림은 기록을 돕는 사용자의 선택 기능으로만 둔다.
- 기록을 기본적으로 사용자의 기기 안에 둔다.
- 검색 서비스는 입력을 돕는 보조 수단으로만 사용하고 직접 등록을 항상 허용한다.

## 대상 사용자

### 핵심 사용자

- 일상과 문화생활을 함께 기록하고 싶은 사람
- 공개 SNS보다 혼자 보는 기록을 선호하는 사람
- 복잡한 분류나 긴 초기 설정 없이 바로 쓰고 싶은 사람
- 영화와 책의 객관적인 정보보다 “내가 어떻게 느꼈는지”를 남기고 싶은 사람
- 장식적인 색 변화 없이 밝고 단정한 화면에서 기록하고 싶은 사람

### 핵심 사용 상황

1. 하루가 끝난 뒤 사진과 함께 짧은 일기를 남긴다.
2. 영화를 본 직후 별점과 여운을 기록한다.
3. 책을 읽는 중이나 다 읽은 뒤 생각을 적는다.
4. 시간이 지난 후 제목, 내용, 저자로 과거의 기억을 검색한다.
5. 당시의 사진, 날짜, 별점과 글을 함께 보며 경험을 다시 떠올린다.

## 사용자가 얻어야 하는 가치

### 1. 기록 시작이 가볍다

로그인, 프로필 작성, 친구 추가가 선행되지 않는다. 제목과 날짜만으로도 기록을 저장할 수 있고 사진과 본문은 선택 사항이다. 영화와 책은 검색 결과를 선택하거나 검색 없이 직접 등록할 수 있다.

### 2. 서로 다른 경험이 한 사람의 기억으로 연결된다

일기, 영화, 책은 별도 탭을 가지지만 동일한 기록 구조와 시각 언어를 사용한다. 사용자는 세 가지 데이터베이스를 관리하는 것이 아니라 자신의 순간을 세 가지 관점으로 모은다.

### 3. 작성 이후에도 가치가 남는다

기록은 저장으로 끝나지 않는다. 목록, 상세, 검색, 날짜 정렬, 수정 기능은 과거 기록을 다시 찾고 현재의 관점으로 보완하기 위해 존재한다.

### 4. 개인 기록이라는 약속이 분명하다

기록은 기본적으로 로컬 SQLite 데이터베이스에 저장된다. 계정, 공개 피드, 광고, 원격 분석을 제품의 기본값으로 두지 않는다. 외부 검색을 사용할 때만 검색어가 Open Library 또는 TMDB로 전송될 수 있다.

## 제품 원칙

### 기록이 검색보다 우선한다

책과 영화 검색은 제목, 표지, 저자와 연도 입력을 줄여주는 도구다. 검색 결과가 없거나 외부 서비스가 실패해도 사용자는 직접 등록으로 기록을 완료할 수 있어야 한다.

### 감정은 점수보다 풍부하다

영화와 책의 별점은 빠른 회상을 돕는 보조 정보다. 순위, 평균 평점, 다른 사람과의 비교로 확장하지 않는다. 본문에 남긴 사용자의 언어가 핵심 기록이다.

### 일기는 평가하지 않는다

일기에는 별점을 요구하지 않는다. 하루를 좋고 나쁨의 단일 숫자로 환원하지 않고 날짜, 사진, 제목과 글로 남긴다.

### 조용한 제품을 지향한다

사용자를 다시 부르기 위한 원격 푸시, 연속 작성 압박, 배지, 공개 반응을 기본 기능으로 삼지 않는다. 알림을 추가한다면 사용자가 직접 설정한 로컬 리마인더처럼 기록을 돕는 목적이어야 하며, 참여율을 높이기 위한 압박으로 사용하지 않는다.

### 데이터 한계를 숨기지 않는다

로컬 우선은 개인정보와 시작 속도에 유리하지만 앱 삭제, 기기 초기화, 분실 시 복구가 어렵다. 사용자가 백업 파일을 내보내 별도로 보관하고, 필요할 때 가져올 수 있게 하되 자동 클라우드 동기화로 확장하지 않는다.

### 기능보다 복구 가능성을 먼저 본다

작성, 수정, 삭제, 사진 선택, 외부 검색은 실패할 수 있다. 저장 중 중복 입력을 막고, 오류 이유를 알리고, 외부 검색 실패 시 직접 등록 경로를 유지한다. 삭제처럼 되돌릴 수 없는 동작은 확인 절차를 둔다.

## 현재 제품 범위

| 영역 | 제공하는 경험 | 의도 |
|---|---|---|
| 일기 | 날짜, 제목, 본문, 사진 기록 | 하루의 감정과 장면 보관 |
| 영화 | 검색 또는 직접 등록, 별점, 감상 | 작품 정보보다 개인의 여운 기록 |
| 책 | 검색 또는 직접 등록, 별점, 독서 노트 | 독서 경험과 생각 보관 |
| 기억 목록 | 최신순·오래된순 정렬, 통합 필드 검색 | 기록 후 재방문 지원 |
| 기록 상세 | 사진, 날짜, 메타데이터, 별점, 본문 | 당시 경험을 한 화면에서 회상 |
| 기록 관리 | 수정, 사진 제거, 삭제 확인, 최근 삭제 30일 복원 | 시간이 지난 기록의 보완과 통제 |
| 전체·설정 | 공지, FAQ, 정책, 문의, 버전, 사진·최근 삭제 포함 백업 내보내기·가져오기와 마지막 내보내기 시각, 선택적 로컬 리마인더 | 사용자가 앱 동작과 데이터 정책을 이해하고 기록을 이동하거나 원하는 때 기록하도록 지원 |
| 시작 경험 | 네이티브 스플래시, OTA 확인, 진행 표시 | 업데이트가 있어도 예측 가능한 진입 제공 |

## 핵심 사용자 흐름

### 일기 남기기

`일기 탭 → 추가 → 날짜·제목·내용·사진 선택 → 저장 → 상세 확인`

제목은 필수이고 사진과 내용은 선택 사항이다. 사용자는 오늘뿐 아니라 2000-01-01 이후의 과거 날짜를 선택할 수 있다.

### 영화·책 기록하기

`영화/책 탭 → 추가 → 외부 검색 또는 직접 등록 → 별점·감상 작성 → 저장`

검색은 입력 보조다. 검색 API 키, 네트워크, 검색 결과 유무가 기록 완료 여부를 결정해서는 안 된다.

### 기억 다시 찾기

`탭 → 검색 → 제목·내용·저자 일치 결과 → 상세 → 필요하면 수정`

검색과 정렬은 보관된 기록이 많아진 뒤에도 앱의 가치가 유지되도록 하는 핵심 기능이다.

## 정보 구조를 나눈 이유

하단 탭은 `일기`, `영화`, `책`, `전체`로 구성한다.

- 세 기록 탭을 분리해 사용자가 지금 남기려는 경험의 문맥을 빠르게 선택하게 한다.
- 목록 행, 상세, 작성 흐름은 공통화해 하나의 기억 보관함이라는 일관성을 유지한다.
- `전체` 탭은 기록과 직접 관련 없는 도움말, 정책과 앱 정보를 모은다.
- 별도의 소셜 홈이나 추천 피드를 두지 않는다. 앱의 첫 화면은 다른 사람의 콘텐츠가 아니라 사용자의 기록이다.

## 데이터와 개인정보 원칙

### 저장 위치

- 기록 본문과 메타데이터: 앱 전용 SQLite 데이터베이스
- 사용자가 새로 선택한 사진과 검색 결과 포스터: 가능한 경우 앱 전용 영구 파일로 보관하는 이미지 데이터. 백업 시 이 파일을 JSON 데이터 URI로 변환
- 시작 상태와 마지막 백업 내보내기 시각: 기기 로컬 저장소
- 계정 및 서버 동기화: 현재 없음
- 백업 파일: 사용자가 직접 공유·보관하는 JSON 파일. v2는 활성 기록과 사진, 아직 30일 보관 기간 안에 있는 최근 삭제 기록을 함께 담는다. 가져오기는 파일을 먼저 검증·미리보기한 뒤 사용자가 확인하면 현재 기기 기록과 최근 삭제 목록을 백업 파일 기준으로 교체한다. 기존 v1 백업도 계속 가져올 수 있다.

### 외부로 나갈 수 있는 정보

- 책 검색어: Open Library
- 영화 검색어: TMDB가 구성된 배포 환경
- 지원 페이지 방문: UULab 웹사이트
- OTA 업데이트 확인: Expo Updates

기록 본문, 별점, 일기 사진을 운영자 서버나 검색 서비스로 전송하지 않는다.

### 현재 한계

- 앱 삭제, 기기 초기화 또는 기기 분실 시 기록을 복구하지 못할 수 있다.
- 삭제한 기록은 기기 내부 최근 삭제에 30일 동안 보관되며, 기간이 지나면 이미지 파일과 함께 자동 정리된다.
- Flutter 구버전과 Expo 신버전은 패키지 ID와 앱 샌드박스가 달라 데이터가 자동으로 이동하지 않는다.
- 구 Flutter 앱의 공개 스토어 배포가 확인되지 않아 저장소에서는 레거시 앱을 종료했다. 내부·QA 기기에 남은 데이터는 자동 이전하지 않는다.
- 백업 파일을 사용자가 별도로 보관하지 않으면 앱 삭제·기기 초기화·분실 시 복구할 수 없다.

## 의도적으로 하지 않는 것

다음 항목은 단순한 미구현 목록이 아니라 현재 제품 방향에서 제외한 기본값이다. 도입하려면 사용자 문제, 개인정보 영향, 운영 비용과 실패 복구 방식을 먼저 문서화해야 한다.

- 공개 프로필, 팔로우, 좋아요, 댓글, 공개 피드
- 다른 사용자의 평점과 비교하거나 순위를 만드는 기능
- 작성 횟수 경쟁, 연속 기록 압박, 과도한 배지와 리워드
- 계정 생성을 기록의 선행 조건으로 만드는 것
- 동의 없는 행동 분석과 광고 목적 데이터 수집
- 외부 검색 실패 때문에 직접 기록도 막히는 구조
- 자동 클라우드 동기화나 계정 기반 백업을 암시하는 카피
- 백엔드와 전송 자격증명 없이 원격 알림이 동작한다고 약속하는 것

## 시각·문체 원칙

### 시각

- 라이트 모드만 제공하며 흰색·회색의 중립면과 단일 딥그린 강조색만 사용한다.
- 상태와 기록 종류는 아이콘·문구·위계로도 구분해 추가 색상에 의존하지 않는다.
- 기록 목록과 설정 메뉴는 기본적으로 평평한 행과 얇은 구분선을 사용한다. 카드와 배경 면은 사진·대화상자처럼 경계를 분명히 해야 하는 콘텐츠에만 사용한다.
- 설정 행의 우측 꺾쇠는 하위 화면 이동에만 사용한다. 백업 내보내기·가져오기처럼 현재 화면에서 실행하거나 시스템 선택기를 여는 동작은 짧은 상태·행동 문구로 구분한다.
- 사진 없는 일기는 제목과 본문이 기록 면을 충분히 사용하도록 장식용 썸네일을 만들지 않는다. 영화·책은 작품 포스터가 정보 구조의 일부이므로 이미지가 없을 때만 종류별 아이콘으로 포스터 자리를 표시한다.
- 빈 화면은 큰 장식 아이콘이나 추상적인 격려 문구보다 날짜와 다음 기록 행동을 왼쪽 정렬로 먼저 보여준다.
- 앱바 아이콘은 별도 원형 테두리 없이 44px 터치 영역을 유지하고, 하단 네 개 탭은 안전 영역을 포함한 한 줄 가로 정렬을 유지한다.
- 기기 테마와 무관하게 같은 라이트 화면과 정보 위계를 유지한다.
- 모든 텍스트는 Pretendard 정적 폰트 패밀리를 명시해 iOS와 Android에서 같은 위계를 유지한다.
- 글자는 11·12·14·15·16·19·24px의 제한된 스케일과 400·500·600·700 굵기만 사용한다. 본문은 400, 목록 제목은 500, 레이블·버튼·앱바는 600을 기본으로 하고 700은 상세 대표 제목처럼 한 화면의 최상위 위계에만 사용한다.
- 작은 글자를 진하게 만들어 중요도를 보완하지 않는다. 보조 정보는 크기·색·간격으로 구분하고 `800/900` 굵기는 사용하지 않는다.

### 문체

- 사용자를 평가하거나 재촉하지 않는다.
- “작성 완료”보다 “기억 저장하기”처럼 제품의 의미를 담되 모호하지 않게 쓴다.
- 오류는 책임을 사용자에게 돌리지 않고 다음 행동을 제시한다.
- 제공하지 않는 기능을 “곧 제공”한다고 약속하지 않는다.
- 개인정보와 데이터 손실 가능성은 감성적인 표현으로 가리지 않는다.

## 성공의 정의

모멘트리의 성공은 기록 수를 최대화하는 것이 아니라 사용자가 부담 없이 기록하고, 시간이 지난 뒤 다시 찾아보며, 자신의 기록을 신뢰하는 데 있다.

현재 앱은 분석 SDK나 사용자 계정이 없으므로 다음 지표를 자동 수집하지 않는다. 향후 측정이 필요하면 최소 수집과 명시적 고지를 먼저 설계한다.

### 확인하고 싶은 제품 신호

- 첫 실행 후 첫 기록을 무리 없이 완료하는가
- 일기뿐 아니라 영화 또는 책 기록도 함께 사용하는가
- 과거 기록을 검색하거나 상세 화면에서 다시 보는가
- 수정 기능으로 기록을 보완하는가
- 데이터 저장 위치와 삭제 시 한계를 이해하는가
- 외부 검색 실패 후에도 직접 등록으로 기록을 완료하는가

### 현재 확인 방법

- 스토어 리뷰와 지원 문의에서 반복되는 문제를 분류한다.
- 출시 전·후 시나리오 기반 수동 QA를 수행한다.
- 기능을 추가할 때 빈 상태, 오류 상태, 오프라인 상태와 복귀 흐름을 검증한다.

## 우선순위 원칙

1. **기록 신뢰성**: 저장, 수정, 삭제, 사진 보관과 복구 가능한 오류 처리
2. **재열람성**: 검색, 정렬, 상세 가독성과 많은 기록에서의 성능
3. **데이터 이동성**: Expo 기록의 백업·복원
4. **입력 편의성**: 검색 품질, 날짜와 사진 입력 개선
5. **선택적 확장**: 사용자가 직접 요청하고 제어할 수 있는 로컬 리마인더

소셜, 광고, 계정, 클라우드 동기화는 위 우선순위를 충분히 해결한 뒤 별도 제품 제안으로 검토한다.

## 운영상 미결정 사항

### 백업과 복원

현재는 `momentry.backup` v2 JSON 파일로 활성 기록·사진과 아직 30일 보관 기간 안에 있는 최근 삭제 기록·사진을 함께 내보낸다. iOS·Android는 시스템 공유 시트를, Web은 파일 다운로드를 사용하며 기존 v1 백업도 계속 가져올 수 있다. 앱은 마지막으로 백업 파일을 만든 시각만 기기에 저장해 설정 화면에 보여주며, 파일이 실제로 기기 밖에 보관되었는지는 단정하지 않는다. 앱 내부에서는 사진과 검색 결과 포스터를 가능한 경우 전용 영구 파일로 보관해 SQLite와 목록 메모리 부담을 줄인다. 네트워크 이미지 다운로드가 실패해도 기록 저장은 외부 URI로 계속할 수 있다. 가져오기는 파일 전체를 검증하고 활성 기록 수·최근 삭제 수·내보낸 시각을 미리 보여준 뒤 사용자가 명시적으로 확인하면 Web에서는 지원 transaction, iOS·Android에서는 exclusive transaction으로 교체한다. 가져온 사진도 앱 전용 파일로 저장하고, 검증 실패나 삽입 오류가 발생하면 기존 기록과 최근 삭제 목록을 유지한다. 백업 파일은 사용자가 직접 기기 밖에 보관하며, 파일 암호화와 선택적 병합은 별도 제품 제안으로 남긴다.

### Flutter 데이터 이전

구 Flutter 앱은 공개 스토어 배포가 확인되지 않아 별도 이전 기능 없이 종료했다. 내부·QA 기기의 데이터 이전 요구가 새로 확인되면 Git 이력의 레거시 스키마를 기준으로 일회성 도구를 별도 설계한다. Flutter 프로젝트 전체를 활성 소스로 복원하지 않는다.

### 영화 검색 운영 방식

TMDB 자격 증명은 소스에 포함하지 않는다. 운영 환경에서 영화 검색을 제공할지, 직접 등록만 유지할지, 프록시를 둘지는 보안과 서비스 약관을 포함해 결정한다.

### 알림

현재 Expo Notifications 네이티브 설정, `momentry` Android 채널, 알림 권한 화면, 로컬 테스트 알림과 사용자가 선택하는 매일 기록 리마인더를 제공한다. 리마인더 시간과 예약 상태는 기기에만 저장하며, 알림을 끄면 예약도 취소한다. OS 설정이나 앱 복원 과정에서 예약이 사라지면 알림 화면 진입 시 저장 상태와 실제 예약을 다시 대조해 잘못된 활성 표시를 해제한다. 원격 Expo Push는 Momentry 전용 Android transport, iOS APNs/EAS 자격증명, 토큰 저장 백엔드와 알림 이벤트 정책이 연결되기 전까지 활성화하지 않는다. 다른 앱의 Firebase 설정을 재사용하지 않는다.

## 새로운 기능을 판단하는 질문

기능 제안은 아래 질문에 답할 수 있을 때 진행한다.

1. 이 기능은 기록을 더 쉽게 남기거나 다시 찾게 하는가?
2. 계정, 공개, 알림 또는 데이터 수집을 불필요하게 강요하지 않는가?
3. 오프라인이거나 외부 서비스가 실패해도 핵심 기록 흐름이 유지되는가?
4. 사용자가 자신의 기록을 수정, 삭제, 이동할 수 있는가?
5. 실패했을 때 데이터가 사라지거나 중복되지 않도록 복구 경로가 있는가?
6. 앱이 실제로 제공하는 범위와 화면·스토어 카피가 일치하는가?
7. 네이티브 변경이라면 OTA가 아니라 새 바이너리로 배포하도록 분류했는가?

하나라도 답이 불분명하면 구현 전에 문제 정의와 데이터 흐름을 보완한다.
